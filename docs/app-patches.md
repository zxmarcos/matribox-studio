# App patches

Effects only change section 1 of the firmware. Some features need the app itself to behave differently; these
are done as **patches of the original app**: small C functions placed in free ITCM, reached from hooks written
over the original code. The original app stays in place, so everything else keeps working exactly as before.

| Feature | Does | Needs |
|---|---|---|
| `parallel` | draws Split … A … Path B … B … Merge as two rows on the main and chain-edit screens, with own icons | the [routing modules](examples.md#parallel) in the library |
| `textlist` | shows parameter values as names from the library (`"options"` in manifests) | — |
| `clonedual` | the Clone menu runs the factory engine or NAM per slot | the NAM Clone module as entry 11.1 |
| `clonetabs` | "Native" / "NAM A2" tabs in the Clone menu | `clonedual` |

```sh
python -m matribox patch-app --features=parallel,textlist BASE.bin OUT.bin
```

Any combination can be built; if the base's app is already patched, the patcher starts again from the
original app of `firmware/QME-200_FW_USB_V1.2.2.bin`. The Studio does the same with "Gerar base do original",
adding the routing modules when `parallel` is chosen. Only section 0 changes (plus section 1 when routing
modules are added).

## How a patch is applied (`matribox/app/apppatch.py`)

1. The C sources of the selected features (`matribox/app/patches/*.c`) are compiled with Zig's clang
   (Thumb-2, soft-float, no PIC) and linked by `patches/link.ld` at **`0x53cc0`**, right after the end of the
   app's ITCM image (`0x53cb9`) and below the effect module pool (`0x58000`): about 17 KB of room.
2. The ITCM image of section 0 grows to include the patch, and the section's load triples are rewritten.
3. Hooks are written into the original code, each one after checking the original bytes (the patcher aborts
   if they differ, for instance on another firmware version):
   - **code hooks**: the first 4 bytes of a function in the ITCM become `b.w <patch function>`; the patch
     re-executes the two instructions it replaced and branches back to `function + 4`;
   - **pointer swaps**: a literal holding a function pointer in the SDRAM image (e.g. the callback passed to
     `GUI_CreateDialogBox`) is replaced by the patch's function;
   - **pokes**: a few bytes replaced in place (an immediate in a `cmp`, a mode number).
4. The `FRMW` checksum is recomputed.

Constraints on patch code: **no `.data` or `.bss`**, since nothing initialises them and no RAM is reserved
(the linker script rejects them); state is read from the app on every call. `const` data is fine (it lives in
the ITCM). Functions reached only through swapped pointers go in `.hook*` sections so the linker keeps them.

SDRAM code (at `0x80000000`) cannot branch to the ITCM with a `b.w` (out of range), but all its calls into the
ITCM go through veneers (`movw ip; movt ip; bx ip`) that keep `lr` intact. So a hook on an ITCM function can
tell **who called it** from `lr`; the parallel patch hooks emWin's `WM_SetWindowPos` and only acts for the three
call sites that position chain blocks.

## parallel: two-row chain display

When the chain contains Split … Path B … Merge in this order:

- **Main screen** (blocks 32×44, widgets `0x820`–`0x82B`): A on the top row (y = 58), B on the bottom row
  (y = 100, starting with Path B), the rest of the chain on the middle row (y = 79); the columns are the
  blocks before Split + max(A, B) + the blocks after Merge, centred.
- **Chain edit screen** (widgets `0x819`–`0x824`): the same, with large blocks (54×76) up to 6 blocks and small
  ones (36×50) from 7, replacing the app's two-row "staircase"; the selection cursor follows.
- **Connector lines** fork after Split and join before Merge on both screens.
- **Icons** for Split, Path B and Merge in all three sizes (orange; grey when bypassed), generated by
  `matribox icons` (`app/mkicons.py`) into `patches/route_icons.h`.

Without Split and Merge nothing changes: the screens are pixel for pixel those of the original app (checked in
emulation). Hooks: `WM_SetWindowPos` (`0xFEC6`) and the dialog callbacks of the main (`0x8000AF98`) and edit
(`0x800037C4`) screens. Known limits: dragging a block **by touch** on the edit screen uses the original
positions to find the drop point; only the first parallel section is drawn.

## textlist: knobs with named options

Every parameter value the UI prints goes through `FUN_00021f94(value, slot, parameter, buffer, size)`. The
patch hooks it: if the parameter's `head` field (−1 in all factory entries, never read by the app) is ≥ 0, it
is the offset of a string `"A|B|C"` in the entry's string table, and the value is shown as option number
`value`. The UI's buffers are 15 bytes, so options have **at most 14 characters**. Manifests set this with
`"options"` ([manifest reference](effects/manifest.md#text-lists-options)); without the patch the pedal shows the
number. The PC editor shows the number too (it formats by its own tables). Example: `examples/multimode`.

## clonedual: factory and NAM engines per slot

The app picks a library entry as `cat_entries[menu][idx]`, with `idx ≥ n` meaning entry 0, in three
functions: copying the module to the staging slot (`0x1B538`), and the memory checks on insert (`0x1B4F4`) and
replace (`0x1B598`). For the Clone menu `idx` is the Clone slot. The hooks replace `idx` by 1 when the slot's
data in flash starts with `"NAM2"` and by 0 otherwise. Two pokes (`0x3960C`, `0x2D35A`) make writing or clearing
a slot reload the chain completely (mode 3) instead of only re-running Init, so the slot's engine follows its
new data. The library gets entry 11.1 (the NAM module, id `0x0F100000`, same knobs as 11.0): the Studio's
"Motor do Clone" option or `build_clone.py --dual`. On a library with a single Clone entry the patch changes
nothing.

## clonetabs: Native / NAM A2 tabs in the Clone menu

The effect-selection screen is the same for every menu; tabs come from three functions that only the UI calls
(subgroup of an entry `0x1EBD2`, number of tabs `0x270C8`, tab name `0x1EB96`). For menu 11 the hooks return
the slot's kind (factory → "Native", NAM blob → "NAM A2"), counting only kinds that are present so that no tab
is empty. Five pokes in the SDRAM code stop the screen from excluding menu 11 from tabs (`sub #0xb; cmp #5`
→ `sub #0xc; cmp #4`). Selecting still returns the slot 0–9; presets, ids and protocol do not change.

## Testing patches without the pedal

`matribox/app/uiemu.py` runs the original app in unicorn: `main` up to the UI loop, with the flash built from
the firmware's sections, then the UI loop a few hundred times, and saves the LCD framebuffer as a PNG. It loads
section 0 from the file under test, so it shows exactly what the pedal would.

```sh
python -m matribox ui-shot OUT.bin main.png 400 --chain=0:0x1b,7:0x1000070,3:0x3000009,7:0x1000071,9:0xb000005,7:0x1000072
python -m matribox ui-shot OUT.bin edit.png 400 --chain=... --screen=2
```

`--chain` builds preset 0 as `menu:id` per position (`!` = bypassed, `-` = empty). `tests/test_qmepreset.py`,
`examples/nam_clone/test_dual.py` and `test_tabs.py` drive the emulated app further: they call the app's own
USB message handlers and check what it does.

## Porting a patch to another firmware version

All addresses are those of V1.2.2. For another version:

1. Rebuild the app ELF (`matribox app-elf NEW.bin app.elf`) and load it in Ghidra. `mkappelf` knows V1.2.2's
   scatter-load handlers; check them first.
2. Free ITCM: read `itcm_size` from section 0 and confirm the module pool still starts at `0x58000`; adjust
   `PATCH_AT` in `apppatch.py` and the origin in `patches/link.ld`.
3. Find each hooked function again by a byte signature of its start (for example `WM_SetWindowPos` begins with
   `70 b5 14 46 0d 46 04 9a 19 46 06 46`; it is emWin code and changes little between builds), and each call
   site and register the patch reads (the `lr` values and the registers holding the block index and count).
4. Update the app data the patches read: the global state (`0x202381A8`, with the current preset at `+0x238`,
   the chain order at `+0x238 + 0x22` and the slots at `+0x268 + 0x44 × slot`), the edit screen's block count,
   the emWin function addresses.
5. Rebuild and compare screenshots in the emulator, with a factory preset (must be identical to the original
   app) and with parallel chains of 6 and 7–11 blocks.

The patcher refuses hooks whose original bytes differ, but it cannot detect a wrong register or struct
offset: the emulator and the checklist are what catch those.
